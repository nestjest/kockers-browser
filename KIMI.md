# Правила разработки Kockers Browser

Эти правила предназначены для Kimi Code и других агентов, изменяющих проект. Контекст архитектуры находится в `CONTEXT.md` и должен обновляться при изменении соответствующего поведения.

## Общий порядок работы

1. Сначала прочитать затрагиваемый код и найти фактическую причину проблемы. Не исправлять по одному знакомому сообщению об ошибке.
2. Сохранять существующие соглашения Rust/Win32, имена и структуру модулей. Не добавлять зависимости, если есть подходящий системный или уже существующий механизм.
3. Не добавлять комментарии, повторяющие код. Комментарии и документацию, описывающие старое поведение, обновлять вместе с изменением.
4. Не исправлять посторонние ошибки и не менять не связанные с задачей файлы.
5. После проверок удалять созданные временные скрипты, журналы и изображения; проверять `git status` и `git diff --check`.
6. Не сообщать об идеальной или визуально проверенной работе, если выполнены только компиляция или проверка `IsWindowVisible`.

## Публикация и пользовательская проверка

- Не коммитить, не перемещать теги и не обновлять GitHub Release без явного запроса пользователя.
- Если пользователь просит дать ему проверить исправление, оставить локальную сборку и не публиковать её до подтверждения.
- Не заменять файлы уже выпущенного релиза без явного запроса. Для обычных исправлений использовать новую версию.
- Перед публикацией показать фактические результаты тестов и реальной установки, не только успешную компиляцию.

## Анимации и UI

### Запрещённые подходы

- Нет bounce, пружин, overshoot и самодельной физики.
- Нет собственного покадрового цикла панелей через `WM_TIMER`, `SetLayeredWindowAttributes` или `SetWindowPos` на каждом кадре.
- Нет `InvalidateRect(window, null, ...)` на всём главном окне для анимации вкладок или их обычных обновлений.
- Нет повторной синхронизации активной вкладки в `on_after_created`, если она уже выполнена при создании/активации.
- Нет безусловного скрытия активной CEF-страницы до `on_load_end`.

### Требуемые подходы

- Использовать короткие линейные переходы по 120 мс и останавливать таймеры в покое.
- Поддерживать настройку `reduce_animations` для нативного UI и CSS.
- Панели показывать и скрывать через системный `AnimateWindow`; иметь fallback на `ShowWindow` и обработчики `WM_PRINTCLIENT`.
- Панели должны быть owned top-level, неактивируемыми окнами. Для ввода использовать `MA_NOACTIVATE`, `SetCapture`/`ReleaseCapture` и корректного владельца через `GW_OWNER`.
- Позиции top-level панелей вычислять через `ClientToScreen` и обновлять при `WM_MOVE`.
- Для вкладок invalidate только изменённую полосу; во время анимации рисовать только её, а не всю панель инструментов.
- При закрытии вкладки сначала завершать out-переход, затем уничтожать CEF-browser. Все способы закрытия должны проходить через общий путь.
- При открытии вкладки активный CEF-контент показывать сразу, фоновый — скрывать.
- Сохранять единую геометрию кнопок заголовка: 36×36 px, скругление 10 px, прежняя увеличенная область нажатия.

### Обязательная UI-проверка

- Проверять реальные клики и результат команды, например смену заголовка на `История — KOCKERS`, а не только наличие окна.
- Для визуальных снимков использовать `PrintWindow`/`WM_PRINTCLIENT`; `CopyFromScreen` может захватить другое перекрывающее приложение.
- Проверять промежуточные и финальные кадры, отсутствие остаточных рамок и возможность повторного открытия после закрытия.
- Для popup дополнительно можно проверять `WindowFromPoint`, но совпадение HWND ещё не доказывает выполнение команды.
- PowerShell-файлы с русскими строками сохранять как UTF-8 с BOM. Не считать проверку успешной, если вспомогательный `Add-Type`, фокус или захват завершились ошибкой.
- Не использовать `Start-Process -Wait` для установщика с `nowait`: PowerShell может ждать всё дерево, включая перезапущенный браузер. Использовать объект процесса и `$process.WaitForExit()` только для установщика.

## Память и жизненный цикл

- Сохранять отложенное создание восстановленных и новых фоновых вкладок при включённой настройке.
- Не копировать URL/заголовки всех вкладок там, где достаточно активного состояния или ID.
- Освобождать snapshots загрузок при закрытии панели и callbacks после завершения загрузки.
- Использовать `LR_SHARED` для подходящих оконных иконок и явно освобождать остальные GDI/GDI+ ресурсы.
- Не нарушать цикл `try_close_browser`/`WM_CLOSE`, `do_close`, `on_before_close` и уничтожение дочернего HWND.
- CEF-вызовы выполнять вне удержания mutex контроллера.

## Обновления и установщик

- Разрешать только HTTPS GitHub и проверять установщик по SHA-256 из релиза.
- Сохранять ожидаемое имя `KockersBrowser-<version>-windows-x64-setup.exe` и файл `SHA256SUMS.txt`.
- Сохранять `CloseApplications=force`, иначе Inno Setup может молча отменить установку с кодом 5 на CEF-процессах.
- После установки проверять код выхода, версию установленной DLL и повторный запуск браузера.
- Поддерживать сравнение четырёхсегментных версий и существующие prerelease/`a`-правила.

## Стандартные проверки

```powershell
powershell -ExecutionPolicy Bypass -File scripts/cargo.ps1 fmt
powershell -ExecutionPolicy Bypass -File scripts/cargo.ps1 test --lib
powershell -Command '& "./scripts/cargo.ps1" -CargoArgs @("clippy","--all-targets","--","-D","warnings")'
powershell -ExecutionPolicy Bypass -File scripts/build.ps1 -Release
powershell -ExecutionPolicy Bypass -File scripts/installer.ps1
```

Не использовать прямой запуск debug EXE вместо CEF bundle. Перед пересборкой закрывать запущенный `target/bundle/kockers_browser.exe`, иначе Windows блокирует DLL.

## Чек-лист нового релиза

1. Обновить `Cargo.toml`, `src/lib.rs`, `build.rs`, `installer/KockersBrowser.iss`, `README.md` и тест сравнения версий.
2. Выполнить форматирование, тесты, Clippy и release-сборку.
3. Собрать установщик, проверить фактическое обновление и перезапуск.
4. Удалить временные файлы и проверить diff.
5. Только после явного разрешения создать коммит и новый тег, отправить `main` и тег.
6. Создать GitHub Release с установщиком, `SHA256SUMS.txt` и русским патчноутом.
7. Проверить `Latest`, имена/размеры assets и совпадение удалённого SHA-256 с локальным. При необходимости проверить наличие тега в `releases.atom`.
8. Не изменять опубликованный релиз после этого без отдельного явного запроса.
